## Linux Command Setup

From an installed Linux checkout, run `bash setup-fusionstudio.sh`. The root Bash entry point resolves its own directory and invokes `install_linux_command.py` with native `python3`. No executable bit is required on downloaded `.sh` files because both setup and the generated command invoke Bash explicitly. The generated executable is `~/.local/bin/fusionstudio`; it quotes the absolute project launcher path and forwards `"$@"`. The existing `start-fusionstudio.sh` selects the Linux virtual environment and runs the app in the foreground.

The Python installer prints the absolute source project, launcher, destination command, temporary command and profile paths. **1/4** checks Linux and calls the existing launcher with `--check` without opening a GUI. **2/4** rejects unmanaged/conflicting commands or incomplete/edited PATH blocks, plans profile writes and prints each backup output. **3/4** atomically publishes its own executable wrapper, backs up existing profiles before appending a marked POSIX-compatible PATH block, and reports progress for each profile. It covers `.profile`, `.bashrc`, Zsh `.zprofile`/`.zshrc` (under exported absolute `ZDOTDIR` when set), plus the first existing `.bash_profile`/`.bash_login`. **4/4** reads back all blocks and checks the installed command's forwarding with `--check`, then removes an intact former managed command wrapper. A failed new-command verification leaves the old wrapper in place.

The PATH block retains existing PATH entries and adds `$HOME/.local/bin` only when absent. Existing profile bytes remain intact before the appended block. Backups use `.fusionstudio-backup-<UTC timestamp>-<unique suffix>`; rerunning an unchanged setup creates no duplicate block or backup. A moved project can update only this tool's marked command by rerunning setup from the new folder. Preflight failures leave commands/profiles unchanged; write-time failures can retain completed steps, with backups identified in the output. No system PATH, administrator privileges or dependency downloads are involved. Bash/Zsh startup files refresh the next terminal; for an existing terminal use `export PATH="$HOME/.local/bin:$PATH"`. Fish and other shell startup formats are not configured.

Migration announces the absolute former `~/.local/bin/ttpselecter` removal target before processing. Only the exact wrapper generated by the former installer is removed, including its ownership marker and quoted absolute launcher target. Unrelated entries and symlinks are retained; edited legacy managed wrappers stop preflight. Existing shell PATH blocks and historical backups are retained. Temporary wrappers and new profile backups now use the `fusionstudio` prefix. The Linux launcher uses `FUSIONSTUDIO_PYTHON` for an explicit native interpreter, otherwise `.venv/bin/python` or `.venv-linux/bin/python`, and forwards all arguments. The old root `.sh` entry points are removed. Reopen the shell or run `hash -r` / `rehash` after migration.

The source program lives beside this README; the root README documents the Bash entry point and generated-command flow. Linux feature-test evidence is separate from command-installer verification.

On 2026-10-22, the renamed command and migration passed **69 assertions** in Kali WSL2 with generated HOME directories under this project, including a failure injected during final new-command verification that retained the former wrapper. No GUI was opened and no personal shell profiles were changed. See the [current report](../artifacts/linux-command-setup/6cb2fcfdaf3840468989a72115dfe814/audit.json). This run uses the installed native Linux Python environment for launcher checks; a generated quoted-path fixture exercises local environment detection and parameter forwarding without opening the application.

## Inputs and Outputs

There are no local input data files. Sources are the official latest-release API, its resolved commit, and files at that immutable commit. At startup, the program prints its Python executable, input status, and absolute output root. Release discovery happens in memory without file writes. Once the version is known, it prints every resolved output path and temporary path before writing files.

A version directory such as `data/attack/v19.2` contains:

- Original Enterprise, Mobile, and ICS STIX 2.1 JSON bundles, named with their version.
- `index.json`: the official catalog index from the pinned commit.
- `release.json`: GitHub release metadata and the resolved commit SHA.
- `LICENSE.txt`: the upstream terms.
- `manifest.json`: version, source URLs, download timestamp, sizes, SHA-256 hashes, and object statistics.
- `README.md`: snapshot provenance and domain statistics.

`data/attack/latest.json` points to the successfully downloaded version using paths relative to that file's directory. The interface should start with the Enterprise bundle.

## Processing Stages and Progress

1. **Discover:** query the latest stable release and resolve its tag to a commit; display each request and the resolved version.
2. **Prepare:** display absolute final and temporary file paths, create the snapshot directory, and save release metadata.
3. **Catalog:** download and validate the official index entries and license; report transfer bytes and percentages when Content-Length is available.
4. **Data:** download each domain to a `.part` file; report transfer progress, validate JSON, STIX bundle structure, collection version, and technique domains; publish each valid bundle and display active tactic/technique counts.
5. **Publish:** save the manifest and snapshot README, then update `latest.json` only after all three domains succeed.

Validation checks are structural and do not implement the complete STIX schema. SHA-256 values are locally computed integrity records, not upstream signatures. Original data keeps revoked/deprecated entries; active counts exclude them and distinguish techniques from sub-techniques.
